abyrd.me: Bun monorepo and personal app

Planning note · July 19, 2026 · no application code or infrastructure has been changed.

What I found

abyrd.me is a single Bun service today: its site, server entry point, Dockerfile, Railway config, and development command all live at the repository root. It already honors Railway’s PORT variable and has a clean route-level test seam.

abyrd-template uses the pattern worth carrying over: one root Bun workspace, deployable packages under packages/, and a Harbor service per long-running package. We should take that shape—not its product packages, database setup, or framework choices.

Recommendation: make the current public site @abyrd/website, add one intentionally small @abyrd/app, and keep both deployable without depending on each other. This gives you a clean home for future personal products without inventing shared packages before there is shared code.

The repository root stays the workspace owner: lockfile, formatting, Harbor, and cross-package commands belong there. Each service owns its server entry point, tests, build/run scripts, and deployment file. A future product feature belongs inside packages/app until a second independent package truly needs the same code.

Root scripts and package contract

{
  "workspaces": ["packages/*"],
  "scripts": {
    "dev": "bun --filter @abyrd/website dev",
    "dev:app": "bun --filter @abyrd/app dev",
    "check": "bun --filter '*' check"
  }
}

Each package will expose its own dev, build, start, lint, typecheck, and check scripts. The exact root aggregation syntax will be checked against the installed Bun version while implementing; the important boundary is that root commands select package scripts by package name.

Private app boundary

packages/app/src/server/auth.ts
  APP_USERNAME + APP_PASSWORD + APP_SESSION_SECRET
    → Effect v3 validates credentials
    → HMAC-signed, HttpOnly session cookie (14 days)

packages/app/src/routes/
  /sign-in  → TanStack Form + Base UI controls
  /         → requires a valid session
  /health   → public deployment check

The app uses TanStack Start because its server functions keep Railway variables server-only. The Base UI button, field, and form primitives follow abyrd-template commit b657c4e; the template’s unrelated product and database layers are not copied.

One choice to confirm

Assumption: Cloudflare should proxy app.abyrd.me (orange cloud) and act as the public edge. This matches Cloudflare’s guidance for HTTP application traffic. Railway’s current custom-domain guide says a proxied Railway domain must use Cloudflare SSL/TLS mode Full, not Full (Strict). If you prefer Cloudflare for DNS only, the record will be DNS-only and Railway’s own TLS certificate will serve visitors directly.

Everything else can proceed with the defaults above. The app’s actual first product, login model, database, and API are intentionally out of scope for this setup pass.

How we will check it

  1. Run one root bun install; confirm the single lockfile resolves both packages.
  2. Run each package’s check, then the root aggregate check. The website’s current routes, 404 behavior, sitemap, and blog tests must remain green.
  3. Start Harbor and confirm both services answer on their assigned local ports; test GET /health on the app.
  4. Build both Docker images from the repository root and run each with a supplied PORT.
  5. Create the Railway app service, deploy it, and confirm its generated Railway domain responds before adding a custom domain.
  6. Add app.abyrd.me in Railway. Copy its exact CNAME and TXT records into Cloudflare, wait for Railway verification, set the selected target port, and test HTTPS plus /health.
  7. If Cloudflare proxying is enabled, set its SSL/TLS mode to Full as Railway requires, then verify the proxied custom hostname has no redirect loop or certificate error.
