Interview Study Hub

Add a private place in app.abyrd.me for daily interview practice and guided courses. It will cover system design, algorithms, programming fundamentals, and web development without adding a database.

Ready to build

What I found

The app is a small Bun workspace package built with TanStack Start, React 19, Tailwind, Base UI, and Effect v3. The home page and server functions already use one signed-in session check. There is no data store today, which makes a browser-local first version the right fit.

The existing primitives cover buttons and fields. The study capability is unique to this app, so it belongs in app-local routes, components, and server modules rather than a new shared workspace package. TanStack Router’s pathless-layout convention lets one authenticated parent own the guard and shared private-app shell without changing public URLs.

What I recommend

One study hub, two ways to learn.

Daily Focus gives a stable, balanced question set for the current day. Practice Another Set gives a new mixed set whenever desired. A separate Courses view teaches a specific problem or pattern, then ends with a focused quiz.

Guard the private application once.

A pathless _authenticated route will perform the signed-in check in beforeLoad and render the shared app shell. The home dashboard and /quiz become its children, so future private tools inherit the same guard automatically. /sign-in and the infrastructure health check remain outside it.

Keep the course system declarative.

Courses, lessons, checkpoints, questions, answers, and final assessments are typed content. Adding a course means authoring one object in the study content module; routes and generic React components do not change.

Store progress in this browser only.

Local storage records the current set, submitted work, flashcard ratings, and course completion. This is intentionally not cross-device and has no Railway database or migration. It can be replaced by a persistence layer later without changing the question or course schema.

The pathless parent is the one UI authorization boundary for the private application: its beforeLoad gets the signed-in session and redirects unauthenticated requests before any child loads. It renders a shared header and an Outlet. The route composes the feature but does not contain selection or grading rules. study.ts is the deep module: it owns the question bank, deterministic daily selection, fresh-set selection, and evaluation. Browser-only persistence has one narrow owner, so a later database migration does not spread storage details through components.

How forms will work

answer-form.tsx will use one colocated useForm instance per written or code question. A keyed question card gives each prompt a fresh form. The answer field validates required non-whitespace content on submit, exposes its error through the existing Base UI field treatment, and awaits the authenticated server function in onSubmit. A form.Subscribe reads only canSubmit and isSubmitting for the submit control.

Multiple choice is intentionally not a form: selecting one option is the complete action, so it calls the evaluation server function directly. Flashcard reveal and “Know it” / “Review again” are likewise direct actions. This keeps Form responsible for actual editable answer data instead of adding state machinery around buttons.

The content shape that makes courses easy to add

type StudyCourse = {
  id: string
  title: string
  summary: string
  outcomes: readonly string[]
  lessons: readonly CourseBlock[]
  assessmentQuestionIds: readonly QuestionId[]
}

type CourseBlock =
  | { kind: "concept"; title: string; body: string }
  | { kind: "checkpoint"; questionId: QuestionId }
  | { kind: "challenge"; title: string; prompt: string; questionId: QuestionId }

A course author adds content to this data shape. The generic course player renders the sequence and launches the final assessment from the listed question IDs. There is no per-course route, component, or special-case state machine.

Open questions and assumptions

Decided: browser-only progress for version one.

Decided: all user-facing private routes live under a pathless authenticated layout. The sign-in page and the existing health probe stay public; this preserves Railway monitoring without exposing app content.

Decided: two initial courses are part of this change, and the content model must make future courses data-only additions.

Assumption: typed code is self-reviewed against a reference answer and rubric. Running arbitrary submitted programs needs a separate sandbox/runtime design and is outside this first private-app feature.

Assumption: “daily” uses the browser’s local calendar date. The date seed gives the same daily focus after refresh, while “Practice Another Set” has its own locally stored attempt number.

How we will check it

  1. Run Bun tests for deterministic daily selection, fresh-set generation, topic/mode balance, answer evaluation, course lookup, and final assessment composition.
  2. Run bun run check from the workspace root. It covers the app’s tests, Biome checks, TypeScript, and the production build.
  3. Start the app and verify the pathless guard redirects both / and /quiz when signed out, preserves the intended destination through sign-in, and leaves only /sign-in and /health public.
  4. Verify the dashboard link, same-day resume, fresh session, flashcard reveal/rating, multiple-choice feedback, typed written answer, typed code answer, and both courses through their final assessment.
  5. Verify the text/code form rejects an empty answer, exposes a field error accessibly, prevents duplicate submission while pending, and accepts a completed response.
  6. Inspect the browser network payload for a loaded question: it must not include a correct option, rubric, or reference solution before feedback is requested.

No external service changes are planned. This branch changes only the app package and generated route tree.
